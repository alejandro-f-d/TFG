\subsection{Casos de uso}

En este sistema, a pesar de que pueden existir numerosos tipos de roles, se pueden catalagar con tres tipos de permisos. Esto se hace para simplificar los casos de uso, a pesar de que cada role puede tener un conjunto de permisos asociados.

\begin{itemize}
  \item \texttt{Administradores:} Los que poseen este permiso son los encargados de dar de alta y de baja a los usuarios a la vez del despliegue de servicios y recursos.

  \item \texttt{Responsables:} Los que poseen este permiso son los encargados de realizar aprobaciones de los permisos de los usuarios base.

  \item \texttt{Usuario base:} Usuario sin permiso que realiza la petición de los servicios a los supervisores. 

  \item \texttt{Cron:}  Proceso encargado de notificar de eventos de calendario/temporales.

  \item \texttt{Healthcheck de las web:} Proceso encargado de notifcar cuando las páginas web se encuentran caidas.
\end{itemize}

Estos son los \textbf{actores} del sistema. Los roles de negocio de la aplicación, mapearían a uno de estos roles de aplicación.

A continuación se describe el flujo operativo del sistema de peticiones, uno de los módulos centrales de la plataforma. El proceso se compone de varias etapas de validación que garantizan la trazabilidad de la solicitud desde su origen hasta su implementación final:

\begin{enumerate}
  \item \textbf{Solicitud inicial y formalización}: El proceso comienza cuando el usuario genera una petición desde la interfaz. El sistema genera un documento PDF que debe ser firmado en primera instancia por parte del usuario.

  \item \textbf{Carga y validación de documentación}: Una vez firmado el documento, el usuario lo carga en la aplicación. Esta acción genera una notificación automática al responsable correspondiente, adjuntando la solicitud para su revisión y solicitando su firma conforme a la normativa del laboratorio.

  \item \textbf{Aprobación jerárquica}: Tras la validación y firma del responsable, el Jefe de Laboratorio recibe una notificación para proceder con la aprobación final. Esta fase representa el último filtro administrativo.

  \item \textbf{Implementación y cierre}: Una vez que la solicitud se encuentra en estado de Aprobada, el administrador del sistema ejecuta las acciones técnicas asociadas. Al finalizar, marca la petición como Implementada en la plataforma.

  \item \textbf{Notificación de finalización}: Como cierre del flujo, el sistema envía una comunicación automática al usuario solicitante, al responsable y al Jefe de Laboratorio, informando que el recurso solicitado está disponible.
\end{enumerate}

\section{Diseño de la solución}

\subsection{Proceso de firma de documentos}

Para el proceso de firma de documentos por parte de los diferentes usuarios del sistema se va a hacer uso del sistema de @Firma estatal vinculado con la sede electrónica del Ministerio para la Transformación Digital y de la función pública. \cite{PAE} 
Este sistema se quiere utilizar para garantizar que el usuario acepta los términos y condiciones de servicio a la hora de hacer uso de los servidores que se proporcionan en el laboratorio. Nos apoyamos en el artículo 26, citando textualmente de la \href{https://sedediatid.digital.gob.es/es-es/firmaelectronica/Paginas/firma.aspx}{página web} \cite{sede_electronica_firma_digital, firma_electronica_ciudadanos}. 

\texttt{(inicio de cita)}
Asimismo, los requisitos de la firma electrónica avanzada se definen en su artículo 26:
\begin{itemize}
  \item estar vinculada al firmante de manera única;
  \item permitir la identificación del firmante;
  \item haber sido creada utilizando datos de creación de la firma electrónica que el firmante puede utilizar, con un alto nivel de confianza, bajo su control exclusivo, y
  \item estar vinculada con los datos firmados por la misma de modo tal que cualquier modificación ulterior de los mismos sea detectable. 
\end{itemize}
\texttt{(fin de cita)}

\subsection{Infraestructura}

La infraestructura se va a basar en microservicios apoyados en docker. El sistema se va a desarrollar en diferentes capas: 
\begin{itemize}
  % \item Frontend: Esta capa va a ser la visible para el usuario y la que está pensada para que el usuario interactue.
  % \item API: Esta capa se encargará de la comunicación entre el frontend y el backend. Además se encargará de trabajar con los servicios de @firma.
  % \item Backend: Esta última capa se va a encargar del almacenamiento de los datos. Concretamente se va a dividir en dos partes principales, una base de datos y en una estructura encargada de almacenar los datos de los documentos (servicio de almacenamiento de objetos).
  \item \texttt{Bases de datos (Tablas del modelo relacional)}: Servicio de almacenamiento para el sistema.
  \item \texttt{Bases de datos (Documentos)}: En este microservicio se van a almacenar de manera segura los documentos, separados de la base de datos para evitar su sobrecarga.
  \item \texttt{API}: Comunicación entre el frontend y el backend.
  \item \texttt{Worker}: Encargado de realización de trabajos pesados tales como la monitorización de páginas web.
  \item \texttt{Frontend}: Parte con la que va a interactuar el usuario. 
  \item \texttt{Cron}: Encargado de realizar tareas periódicas con el worker.
  \item \texttt{Digital Signature Service}: Servicio de la Comunidad Económica Europea para validar la integridad de firmas en documentos PDF.
  \item \texttt{Frontend}: Capa visible para el usuario y con la que interactua el usuario. 
  \item \texttt{Apache Tomcat}: Gestor de servicios Apache para @firma. Este servicio aprovecha los certificados del nginx para su comunicación segura. Este servicio se podría utilizar para algún caso de uso adicional en caso de ser necesario en un futuro.  
\end{itemize}

Se selecciona una arquitectura modular basada en docker ya que estos sistemas permiten aislamiento y portabilidad con respecto a las características de la máquina. En un sistema de mayor cantidad de usuarios que en el caso de este laboratorio permitiría una mayor resilencia con el uso de herramientas como un loadbalancer que opere con diferentes instancias de la API levantando instancias según sea necesario con orquestadores como Kubernetes. En la parte del almacenado de datos, este sistema permitiría la redundancia de datos del sistema en varias bases de datos si fuera necesario.

\section{Implementación y codificación}
\subsection{Backend}

\subsubsection{Autenticación y middleware}
Para la autenticación de los usuarios se ha utilizado el sistema de Bearer Token, este sistema funciona mediante la generación de una contraseña firmada por el servidor que es capaz de identificar al usuario. En el caso de esta implementación, este token guarda el uuid del usuario se trata de un identificador único para cada usuario. Para el sistema de permisos se ha desarrollado un sistema de identificación basado en roles, por ello para cada petición que recibe la API, el middleware se encarga de validar la petición para permitir o denegar el acceso. 

\subsubsection{Almacenamiento de la información}
Para el almacenamiento de la información este sistema se apoya en tres bases de datos, una de ellas relacional para almacenar la información de forma estructurada de los usuarios, servicios y máquinas. 
Los documentos se guardan en un sistema de almacenamiento permanente de objetos. Adecuado para el payload evitando bases de datos SQL y NoSQL.
Por otro lado, se usa una base de datos redis (\textbf{NoSQL}) para el intercambio de transacciones rápidas entre la api y el worker, como el envío de correos electrónicos y generación de documentos \cite{pdfkit_generator}. \cite{thepower_redis}.

\subsubsection{Validación de los datos de entrada API}
Para la validación de los tipos de entrada y de los parámetros obligatorios se hace uso de JOI así como las longuitudes como capa extra de seguridad hacia la API evitando así buffer overflows y errores de tipos.

\subsubsection{Validación de los datos de entrada PDF}

En el marco teórico los pdf firmados digitalmente están compuestos por un ByteRange, este es el encargado de separar las segmentos del documento firmado y la propia firma digital. \cite{sign_verification} 

Este sistema, al usar firmas con validez legal, tienen una estructura más compleja. Por ello se utiliza un sistema de organismos oficiales para validar la firma. En este caso, se utiliza un herramienta instalable en local de la \texttt{Comisión Europea}. Se trata de una API REST, que valida todas las firmas de un documento. Más información se puede encontrar en \href{https://ec.europa.eu/digital-building-blocks/sites/spaces/DIGITAL/pages/467109107/Digital+Signature+Service+-+DSS}{Digital Signature Service} (DSS en adalente) y el \href{https://github.com/esig/dss-demonstrations}{Repositorio Oficial de Documentación}. \cite{github_dss} 

Este sistema al estar gestionado integramente por el laboratorio puede proporcionar mayor confidencialidad de los documentos firmados.

\subsubsection{CRON}

Para las actividades con una perioricidad determinada se hace uso del servicio de CRON de node-js \cite{cron}. De esta manera permitimos la realización de las mismas por parte del \textbf{worker} en un momento determinado. Entre otras se encargará de tareas como: recordatorios de fin de servicios y de estancia de usuarios en el laboratorio. 


\subsection{Diseño lógico del proceso de firma}

El proceso de firma se puede ver en la figura\ref{fig:detalle_firmas} a través de un flujo dividido en dos etapas. En la primera de ellas, tras la solicitud del servicio por parte del usuario, la API gestiona la creación de un PDF mediante el worker del sistema \cite{pdfkit_generator}. En este documento se le añade una firma única del servidor autofirmada, que aunque carece de validez legal cumple con los requisitos de la trazabilidad y verifica que no se le envía otro pdf distinto. Seguidamente, se inicia la fase de firmas propiamente dicha: una vez que el usuario firma y envía el archivo desde la web, el revisor recibe un aviso para validarlo, permitiendo que el documento avance hacia la autorización final del jefe de laboratorio. Además, en cada una de estas entregas, el sistema realiza una validación interna con el DSS para verificar la autenticidad de la firmas electrónicas y que se encuentra presente y validada la original del servidor.
