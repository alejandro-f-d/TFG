La integración técnica se realiza mediante contraseñas de aplicación. El sistema de correo electrónico trabaja con un modelo editor suscriptor donde hay presentes diferentes tipos de editores. Entre los editores se puede encontrar a la API que delega la tarea de envío de correos electrónicos al Worker y el sistema de monitorización y el cron con su servicio de notificaciones. \section{Integración de terceros Gitlab}

\subsection{Descripción del servicio instalado}

La arquitectura actual del sistema se basa en un microservicio desplegado mediante \texttt{Docker}. Tras analizar las diversas metodologías de integración con servicios externos, se ha determinado que el mejor diseño consiste en establecer una comunicación vía \textbf{API}, empleando la autenticación mediante \textbf{tokens de usuario} para garantizar la seguridad y eficiencia en el intercambio de información. \cite{GITLAB_TOKEN}

\subsection{Operaciones permitidas con este servicio de terceros en la página web:}
El sistema permite las siguientes operaciones con este servicio de terceros:

\begin{itemize}
\item \texttt{Creación de nuevos usuarios en el sistema.}
\item \texttt{Modificación de nombres de usuario de cuentas existentes.}
\item \texttt{Bloqueo de usuarios.}
\item \texttt{Creación de nuevos repositorios en el namespace del usuario root.}
\item \texttt{Obtención de información general de un proyecto, incluyendo estadísticas y historial de commits.}
\item \texttt{Consulta de repositorios con estadísticas para usuarios individuales y grupos.}
\item \texttt{Modificación de los colaboradores de un repositorio, a excepción del owner.}
\item \texttt{Gestión de acceso en repositorios de grupo, permitiendo añadir usuarios como invitados sin modificar la configuración del grupo.}
\item \texttt{Archivado y desarchivado de repositorios.}
\item \texttt{Sincronización automática mediante un worker que mantiene actualizada la base de datos interna con la información más reciente de los repositorios.}
\end{itemize}

Todo esto se realiza mediante la integración a través de la cuenta de \textbf{root}.

A pesar de estas posibilidades el trabajo actual tiene ciertas limitaciones:
\begin{itemize}
\item \texttt{La creación de repositorios está restringida al namespace del usuario root; no es posible crearlos en namespaces de otros usuarios o grupos.}
\item \texttt{No es posible modificar al owner de un repositorio.}
\item \texttt{La gestión de usuarios en repositorios de grupo opera únicamente a nivel de invitado, sin posibilidad de modificar roles internos del grupo.}
\item \texttt{No se contemplan operaciones sobre grupos como creación, edición o eliminación.}
\item \texttt{No hay soporte para otras entidades de GitLab como issues, merge requests o pipelines.}
\end{itemize}

\subsection{Armonización de datos}

Con el objetivo de mantener una única fuente de verdad, se necesita un proceso de armonización y extracción de la información de los datos de los repositorios. Para ello se diseña el siguiente flujo ilustrando en la figura \ref{fig:flujo_gitlab}, que puede iniciarse con dos disparadores, mediante un cron que realizará la ejecución autónoma del proceso o con un evento de alta de usuario recibido a través de la cola de mensajes. Independientemente del disparador, ambas vías convergen en el orquestador, que es el componente encargado de iniciar y coordinar el proceso completo de armonización.

El flujo sigue los siguientes pasos. En primer lugar se itera sobre todos los usuarios con identificador de gitlab presente en el sistema, para cada uno de ellos, se extrae primero todos los grupos de los que es participante, con esto se extraen cada uno de los repositorios presentes en los grupos. Con esta información se nutre la base de datos con la información de proyectos y la relación de participantes. Una vez se ha terminado con los grupos, se hace lo mismo con los repositorios personales. Por último, se hace una limpieza iterativa verificando si los repositorios almacenados siguen estando o han sido eliminados para eliminarlos del sistema.

\begin{figure}[H] 
 \centering 
 \includegraphics[width=0.5\textwidth]{incremento-iv/diagrama_gitlab.png}
 \caption{Flujo de armonización de datos.}
 \label{fig:flujo_gitlab}
\end{figure}



La integración actual cubre las operaciones esenciales de gestión de usuarios y repositorios, pero aún existe un amplio margen de mejora. El trabajo se podría extender a la creación de repositorios a namespaces de otros usuarios y grupos, ampliar la gestión de roles más allá del nivel de invitado en repositorios de grupo, e incorporar operaciones completas sobre grupos. A más largo plazo, se puede contemplar una mayor cobertura de la API de GitLab para dar soporte a entidades como issues, merge requests y pipelines, con el objetivo de ofrecer una integración más completa y autónoma desde la propia aplicación.

\section{Marco teórico Integración de Terceros Sistema de identificación de usuarios (SIU UPM)}

En este punto, nos encontramos en la situación de que el sistema debe permitir al usuario identificarse de manera segura. Podemos encontrar principalmente dos tipos de usuarios.

 \begin{itemize}
   \item \texttt{Usuarios con vinculación a la UPM}. En este grupo encontramos a los estudiantes y el personal docente e investigador entre otros. \cite{siu_upm}
   \item \texttt{Usuarios sin vinculación a la UPM}. Este grupo de usuarios, no tienen ninguna asociación con la universidad, serían un grupo muy pequeño y acotado. Se encontrarían principalmente estudiantes (ajenos a la universidad) e investigadores (ajenos a la universidad) con vinculación en el laboratorio MEDAL.
 \end{itemize} 

\notaseguridad{Se debe destacar que el sistema de identificación única, en adelante SIU, se trata de un sistema más seguro que un sistema implementado propio para este trabajo fin de grado. Esto se debe a que se trata de un sistema probado y mantenido por personal experto.}

En primera instancia, el objetivo es utilizar el SIU para el personal asociado a la UPM al cual de manera interna en el servicio se le aplicará una access control list (ACL) para filtrar los usuarios que tienen permitido el acceso. Para los usuarios sin vinculación a la UPM, se crearía un sistema parecido al ofrecido por la UPM pero interno al laboratorio.
